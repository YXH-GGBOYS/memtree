# 上下文经济学

[English](context-economics.md)

## 成本模型

一个 Claude Code 会话就是一串模型调用。第 *i* 次调用会把到目前为止的整段对话发出去，记作 `c_i`
个 token（系统提示、工具定义、CLAUDE.md、每条消息、每个还在上下文里的工具结果）。一个会话花的钱、
占的速率额度，大致是 `Σ c_i`。

上下文随着干活不断变大。假设会话从 `b` 个 token 起步，每次调用平均多 `a` 个，那么 `N` 次调用之后
`Σ c_i ≈ N·b + a·N²/2`。第二项才是要命的：会话长一倍，增长部分要多付约四倍。提示缓存让重复发送的
token 便宜一些，但不是免费，而且照样占上下文窗口。

两个推论：

- 早进上下文的东西，之后每次调用都要再付一遍。一个 400 次调用的会话，第 50 次读进来的 20 KB 工具
  结果，后面还要再发大约 350 次。
- 缩短会话比抠单次读取省得多，因为它直接去掉了大部分 token 所在的那些大上下文调用。

## 我们量到了什么

数据来源：一位独立开发者本机的 Claude Code 会话记录。取 21 天窗口里（美东 2026-10-22 至
2026-11-11，按每次调用自己的时间戳）主会话的全部调用：147 个会话、37,529 次调用、17 个项目。
子 agent 和 workflow 的记录另算。每次调用的上下文用会话记录里的真实用量：`input_tokens +
cache_read_input_tokens + cache_creation_input_tokens`，在全部记录之间按 message id 去重。只公布
比例和次数。

| 问题 | 结果 |
|---|---|
| 重复发送的上下文里，有多少来自同一会话里重读同一个文件？ | 约 0.1%，几乎都是图片又读了一遍；读回来内容一字不差的：约为 0 |
| 有多少发生在上下文超过 30 万的调用里？ | 约 76% |
| ……超过 50 万的？ | 约 43% |
| 一个全新的会话，还没干活时有多大？ | 中位数约 9.6 万 token，多数在 8.3 万到 12.1 万之间（工具、系统提示、CLAUDE.md） |
| 一个常见关键词查知识文件：grep 对比卡片查询 | 输出约 500 KB 对约 4 KB |

第一行出乎我们意料：「别把同一个文件读两遍」几乎无关紧要。第二、三行说明 token 在哪：在那一长串
大上下文的调用里。

第四行的固定开销是一个下限。换会话换得太早是浪费；在那套环境里，新会话读完卡片和几个指针，实际
大约从 15 万起步。

### 量自己的记录时容易数错的两处

这组数字第一次跑的时候犯了两个计数错误。`token_report.py` 现在两处都避开了；如果你用别的办法量，
要留意。

- 按文件修改时间挑会话，会混进老会话。Claude Code 会在会话最后一次调用之后很久，还往记录末尾追加
  元数据行，所以「最近三周改动过的记录」里有不少几周前就结束的会话。第一次那个「三周」里，主会话
  调用约四成其实早于窗口，最早的早了约两个月。应该按每次调用自己的 `timestamp` 筛。
- 分叉、复制出来的会话会把同一批调用算两遍。分叉会新开一份记录，里面带着父会话的历史，message id
  不变。21 天窗口里，主会话有 7.6% 的调用是这种副本。去重要跨全部记录按 message id 做，不能只在一份
  记录里去。

两处都改掉之后，总量少了将近一半，比例几乎没动：上下文超过 30 万的调用占比从约 77% 到 76%，超过
50 万的从 46% 到 43%，下面 45 万 / 15 万的换会话节省从 31% 到 30%。

## 换会话模拟

`scripts/token_report.py` 把每个记录下来的会话重放一遍，假设它每当上下文超过门槛 `T` 就换到新会话，
新会话从 `R` 起步：

```
offset = 0
对每次真实上下文为 x 的调用:
    y = x - offset                 # 这次调用的模拟上下文
    if y > T:                      # 换会话: 新会话从 R 起步
        offset = x - R; y = R
    floor = min(x, R)
    if y < floor:                  # 真实会话变小了（压缩）: 不会低于新会话的起点
        offset = x - floor; y = floor
    simulated_total += y
节省 = 1 - simulated_total / real_total
```

换会话之后，模拟会话完全照真实会话的样子增长。在实测数据上取 `T = 45 万`、`R ≈ 15 万`，节省约 30%。早一版模拟在同一份数据上算出 35%-40%：原会话自己压缩之后，它让模拟会话一直停在
`R` 不再增长，多算了节省。上面 `floor` 那一步就是修这个的。

模拟没算的东西，所以这个数要当上限看：

- 卡片本身，以及新会话按指针读的文件（一部分已含在 `R` 里）；
- 交接中丢失的信息，以及由此带来的返工；
- 会话变短之后人的工作方式可能也会变。

在你自己的记录上跑：

```bash
python3 scripts/token_report.py --since 2026-10-01
python3 scripts/token_report.py --since 2026-10-01 --until 2026-10-22
python3 scripts/token_report.py --project my-app --simulate 300000:120000 --out report.md
```

`--since` 和 `--until` 是本机时区的日期；一次调用自己的时间戳落在两天的 0 点之间（不含 `--until`
那天）才算。它只在本机读 `~/.claude/projects/**/*.jsonl`，不往任何地方发数据。「carry」表里按来源分的大小是按
字符数估的；每次调用的上下文数字是真实的。

## MemTree 怎么用这些结论

| 发现 | MemTree 的做法 |
|---|---|
| 大上下文调用占了大头 | `ctx_handoff_reminder.py` 在窗口的 45% / 60% / 75% 各提醒一次；`memtree-handoff` 让换会话很便宜 |
| 注入的东西会一直留到会话结束 | `facts_digest.py` 每个会话只注入一次摘要，之后只给一行指针；`post_compact.py` 只在压缩后重注 |
| grep 知识文件一次返回几百 KB | `memq.py` 每个条目只回一张卡片，再用 Read 带 offset/limit 取细节 |
| hook 输出超过 10,000 字符就变成文件加约 2,000 字符预览 | 每个 hook 都控制在 9,000 字节以内，截断时留可见标记 |

摘要注入的量级：一个 1,000 token 的摘要，如果一个会话的 100 条消息每条都注入，上下文里就有 100 份，
每份之后的每次调用都要再发。每会话只注入一次，就只有一份。
